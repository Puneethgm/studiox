The fake "verify you're human" popup some customers reported (the "ClickFix" attack).

What customers saw: a popup on a page of ours that looked like a CAPTCHA/human-verification check, but instead of a checkbox it told them to open their computer's Run dialog or Terminal and paste in a command. That command, if run, downloads and executes malicious code on their machine. This is a well-known scam technique called "ClickFix" (sometimes paired with a delivery method called "EtherHiding", where the actual malicious code is fetched from a blockchain smart contract at the moment it runs, so it's hard to spot by just looking at the page's saved source).

What I checked on our side, in detail:
- Went through our nginx config on the server line by line — no rule that injects, rewrites, or appends anything into the pages we serve.
- Went through the Next.js middleware (apps/web/src/middleware.ts) — it only stamps one internal header for admin pages; it doesn't touch what gets rendered to a visitor.
- Checked every script we intentionally load on these pages (Google Tag Manager, Stripe.js) — all are the real, official scripts from Google/Stripe, nothing swapped or tampered with.
- Checked our build output and deployed files for anything unexpected — found nothing injected into our own code or assets.
- Found no trace anywhere on the server of the kind of script that produces this popup.

Conclusion: I could not find any evidence this is coming from our server or our code. The pattern (fake CAPTCHA -> paste a command) is almost always caused by something on the visitor's own computer or browser — most commonly a malicious browser extension, or sometimes a bad ad/script from a completely different website they had open at the same time, that then overlays or injects itself into whatever page they're currently looking at, including ours. In other words, it can make it look like it came from our site even when it didn't.

Root cause: not something on our platform. The most likely source is a malicious browser extension installed on the affected customer's own browser (occasionally a bad ad/script from an unrelated site, with the same effect), which overlays or injects the fake CAPTCHA onto whatever page the person is currently viewing — including ours, which is why it looked like it came from us. We confirmed this by checking every place our own server or code could have caused it (nginx config, middleware, the scripts we intentionally load, build output, deployed files) and found nothing there. So the infection point is the customer's device/browser, not anything we control.

What we did anyway, as a precaution: added a security header (Content-Security-Policy) to both the main platform and the FS8 landing page. In plain terms, this tells the browser "only run scripts that come from this exact approved list of sources, and never run code that's been hidden/encoded and then executed with eval()" — eval() is specifically the technique this kind of attack uses to run its hidden payload. So even in a scenario we haven't thought of, this closes that specific door on our own pages. This is now live on both sites.

What this does NOT fix: if the popup is coming from something installed in the customer's own browser (an extension), our header change can't stop that — it would still show up on any website they visit, not just ours. The real fix for them is on their end: remove suspicious browser extensions, reset browser settings, and run a malware scan (Malwarebytes or Windows Defender/Mac equivalent). If they already ran the command the popup told them to, they should also change their important passwords and check for unfamiliar startup items/scheduled tasks on their computer.

Bottom line: not something we found broken on our platform, but we hardened it anyway since it costs us nothing and closes a real attack technique. The actual cause, as far as we can tell, is on the individual customer's device.
